# Limits: справка по объектам

Здесь описаны данные и методы сервиса. Нужные изменения для ЛР1 перечислены в [TASK.md](TASK.md).
Часть методов уже реализована в заготовке, остальные добавляются по мере выполнения работ.

## Данные и поведение

Сервис лимитов получает сумму покупки и уже рассчитанные расходы. Он проверяет ограничения, но не записывает новую операцию в историю.

`LimitCheckContext(amount: Money, spent_today: Money, spent_month: Money, contactless=False)` хранит данные одной проверки. Суммы уже приведены к валюте счёта.

| Поле или метод | Условие |
|---|---|
| `amount` | Строго положительная сумма покупки. |
| `spent_today`, `spent_month` | Неотрицательные суммы успешных списаний до текущей покупки; `spent_today <= spent_month`. |
| Валюта | Одинакова у всех трёх сумм. |
| `projected_today()` | Возвращает `spent_today + amount`, не меняя исходные расходы. |
| `LimitsService.check(context) -> CheckResult` | Проверяет правила по порядку и возвращает первый отказ. |

Контекст и результат не изменяются через публичный интерфейс. `Money`, `CheckResult` и исключения уже реализованы.

Общий интерфейс — `LimitRule.check(context) -> CheckResult`. `TransactionLimit(maximum)` ограничивает одну покупку, `DailyLimit(maximum)` — сумму дня с учётом покупки. Равенство пределу допустимо. Пустой набор правил не задаёт дополнительных лимитов, но не отключает проверку корректности контекста.

## Работа с готовым кодом

Обращение к сервису выполняется через `app/api.py`. Разрешённые файлы указаны в [TASK.md](TASK.md).
Проверки используют подготовленные данные и не зависят от работы других групп.

До ЛР5 сборка предоставлена готовой. Нужные объекты могут создаваться в сервисном модуле; `assembly.py` менять не нужно.

## Ошибки и результаты

`DomainError` содержит код ошибки. При отказе проверки состояние объекта не должно меняться.
Ошибка переданной зависимости не заменяется успешным результатом. Конкретные коды и примеры
приведены в задании и открытых тестах.
